01

Put the scope in an Excel sheet

· What travels, what is modified by hand
Produce one inventory that every later step quotes, and prove nothing the module needs sits outside it.
  1. List the entities under the module area from the sitemap.The query is in Verification. It is the starting point, not the answer.
  2. Sweep what is not in the sitemap.Stored procedures, functions, SQL data types, workflows and all entities the area never displays. Read the code, not just the navigation.
  3. Classify every entity as native or shared.Native travels inside the solution. Shared already exists in the target and is reconciled by hand there.
  4. Write the special work each shared entity needs.Regarding fields, extra lookups, buttons — recorded next to the entity name, because this is the only place that work is scheduled from.
  5. Build the solution from the native entities with their assets and dependencies, then remove every shared entity and shared web resource from it.
  6. Version the sheet and freeze it in the release folder.Later steps quote it. It has to stop moving before the export.
Exit gate
The sitemap is not the dependency graph

An entity can be absent from the area and still be essential — reached only from a plugin, a stored procedure or a lookup on a form. The code sweep finds more than the query does.

Rebuilding the solution re-pulls dependency chains

Adding one entity drags its own dependencies back in, which can quietly restore a shared component you deliberately excluded. Re-run the exclusion pass after any rebuild.

Diff in both directions

Entities in the sheet but not in the solution is the obvious check. Entities in the solution but not in the sheet is the one that catches dependency chains pulling shared components back in behind you.

Criteria workbook

Download the template, keep the two header rows and the five column groups where they are, then load it back to refresh the counts, the inventory tables, the hosted-resource list in step 02 and the object list in step 04.

-- The area inventory, run in either organisation.
SELECT sub.Name, sub.EntityId
FROM SubAreas sub
JOIN Groups g ON sub.GroupId = g.GroupId
JOIN Areas  a ON g.AreaId   = a.AreaId
WHERE a.Name = 'Hourly Sales'
ORDER BY sub.Name;
02

Hosted feature resources

· Added to the solution before the export
Get the hosted HTML and JavaScript that makes the feature usable into the package, with every reference resolving.
  1. Add each hosted resource to the solution before the export.
  2. Resolve what each page pulls in.Hosted pages load scripts, styles, images and other web resources. Every reference has to be either inside the solution or already present in the target.
  3. Register each variant of the generated POS and dispatcher pages the target needs.The names carrying a suffix are templates; the target needs one registered instance per variant it will actually open.
  4. Remove environment-specific values from the markup.Absolute URLs, organisation names and server names embedded in HTML have to become relative or configurable before the page moves.
  5. Confirm the pages that call the backend point at a configured endpoint, not a literal one.
Exit gate
A hosted page fails quietly

A missing script reference does not break the import. The page loads, the console fills, and the feature is simply inert. Open each one after import rather than trusting the component count.

Open every page after import
  • Each hosted page renders and the browser console is clean.
  • Every referenced script, style and image resolves in the target.
  • The solution component list contains the feature assets before the export begins.
03

Export and import the solution

· The first write into the target
Move the native entities and their assets into the target without disturbing anything that already lives there.
  1. Export from the source after the sheet is frozen.Never reuse an earlier package.
  2. Remove the sitemap from the solution.A sitemap is one component that replaces the target's entire navigation. Build the area by hand in the target instead.
  3. Remove the application ribbon.Entity-level ribbons are fine; the application ribbon is global and overwrites the target's.
  4. Leave every system-settings export option unticked.Auto-numbering, calendar, customisation, email tracking, general, marketing, Outlook synchronisation, relationship roles, ISV configuration — each one is organisation-wide.
  5. Export unmanaged.Reconciliation work in the target needs the imported components to be editable.
  6. Store the package with a checksum and its component list in the release folder.
  7. Raise the import timeouts on the target before starting.A solution this size can exceed the default on-premises timeout, and a timed-out import leaves a partial state that is harder to diagnose than a clean failure.
  8. Import, choosing to maintain the target's customisations wherever the choice is offered.
  9. Read the full import log XML, not the on-screen summary.Record a written decision against every warning.
  10. Publish all customisations, then build the module area in the target sitemap by hand.
Exit gate
STOPThe sitemap is the highest-consequence component in the package

It imports without a warning and replaces navigation for the whole organisation. Users of the other modules lose their menus. Confirm it is out before you export, and again in the component list before you import.

A failed import is rarely a no-op

Components are created as the import goes. A failure at 70% leaves entities present but relationships, forms and views missing — a state that looks fine in the entity list. Restore from backup rather than retrying on top of it.

Publish is not optional and not instant

Until customisations are published, forms and scripts can still run against the old metadata. Verify in a fresh session, not a cached one.

-- The area inventory, run in either organisation.
SELECT sub.Name, sub.EntityId
FROM SubAreas sub
JOIN Groups g ON sub.GroupId = g.GroupId
JOIN Areas  a ON g.AreaId   = a.AreaId
WHERE a.Name = 'Hourly Sales'
ORDER BY sub.Name;
-- Regression guard: diff against the baseline captured before the import.
SELECT a.Name AS AreaName, COUNT(*) AS SubAreas
FROM SubAreas sub
JOIN Groups g ON sub.GroupId = g.GroupId
JOIN Areas  a ON g.AreaId   = a.AreaId
GROUP BY a.Name
ORDER BY a.Name;
04

Database objects

· Calendar table, helper, types, functions, procedures
Deploy the SQL layer the module runs on, in dependency order, into the right database.
  1. Connect the query window to the target database and confirm it in the title bar.The script carries no USE statement, so it deploys into whatever the session is connected to. Make the check part of the ritual.
  2. Deploy in dependency order.Calendar table and table types first, then the helper and date functions, then the procedures that consume them.
  3. Seed the calendar table across the full booking horizon, with years of headroom.Availability joins to it. Short coverage returns an empty calendar and no error.
  4. Grant EXECUTE on the new objects to the account the backend services run as.
  5. Compare a real execution of the availability procedures against the source and add any index the target needs.The same procedure over a different data distribution can be an order of magnitude slower.
  6. Record the deployed object list with modify dates in the release folder.
Exit gate
STOPWithout a USE statement, the connection decides the database

An editor window left on the wrong connection deploys the whole script into the wrong organisation, silently and successfully.

An empty calendar is indistinguishable from no availability

Every availability procedure returns an empty set rather than an error. Verify the coverage before anyone tests the feature and concludes it is broken.

These procedures read base tables directly

They query the physical tables rather than filtered views, so they bypass CRM security and depend on column names. A metadata change in the target can break them with no warning at the application layer.

-- 1. Routines and table types, with fresh modify dates.
SELECT name, type_desc, modify_date FROM sys.objects
WHERE type IN ('U','P','FN','IF','TF')
  AND name IN ()
ORDER BY type_desc, name;

SELECT name FROM sys.table_types
WHERE name IN ('ChosenParameterType','ManualOrderReservationType');

-- 2. Calendar coverage against the booking horizon.
SELECT COUNT(*) AS [Rows], MIN([Date]) AS FirstDate, MAX([Date]) AS LastDate
FROM dbo.DateTable;

-- 3. Unresolved references. Every row is a runtime failure waiting.
SELECT OBJECT_NAME(d.referencing_id) AS ObjectName, d.referenced_entity_name AS MissingObject
FROM sys.sql_expression_dependencies d
WHERE d.referenced_id IS NULL AND d.referenced_entity_name NOT LIKE '#%'
ORDER BY ObjectName;

-- 4. Smoke test with a real service id from the target.
EXEC dbo.GetTimeSlotsByServiceId @serviceId = '<a service id in the target>';
05

Publish the backend projects

· Three services the module runs on
Publish the last stable version of each backend project against the target organisation.
  1. Publish the last stable version of Hourly Module.The custom workflows and APIs SwiftSoft itself calls.
  2. Publish the last stable version of Hourly API.The APIs consumed by the web and mobile clients.
  3. Publish the last stable version of Driver API.The APIs consumed by the driver mobile app.
  4. Point all three at the target organisation.Connection strings, organisation name and unique name, discovery and service endpoints.
  5. Search the deployed configuration for the source organisation and server names.Expect zero hits. This is a search, not a review.
  6. Record the published version of each project in the release folder.
Exit gate
STOPA leftover source connection string writes into the live source

A service published for the target but still pointed at the source looks like a successful deployment: requests succeed, data comes back, tests pass. Meanwhile new records are written into the old organisation. A successful call is not evidence of the right database.

Publish the stable tag, not the working branch

Three projects published from three different commits is the hardest class of defect to diagnose later. Take all three from the same known-good release.

-- Run against the SOURCE database.
-- Any row is a service from the new deployment still pointed at the source.
SELECT s.login_name, s.host_name, s.program_name, s.login_time
FROM sys.dm_exec_sessions s
WHERE s.database_id = DB_ID('')
  AND s.host_name <> '<the known source app server>'
ORDER BY s.login_time DESC;
06

Seed the configuration data

· Configuration only, no history
Populate the lookup and configuration records the module needs, in foreign key order, owned by users that exist.
  1. Decide the identifier policy and write it down.Preserving source ids keeps hard-coded references working and makes a re-run idempotent; it also collides if the target already holds that id. Check for collisions before choosing.
  2. Seed the independent lookups first.Timeslots, recurrence options, relation types and definitions, procedure statuses and types, service groups, price factors, evaluation criteria.
  3. Then the primary records.Services, resources, price lists and templates, promotions, official vacations, providers.
  4. Then the junctions.Service to region, timeslot, price list, resource group, condition group, recurrence option and vacation; region to resource and timeslot.
  5. Remap ownership on every row to users that exist in the target.Owner, owning business unit, owning team, created-by and modified-by. Source user ids do not exist here; rows owned by them are invisible or fail their foreign key.
  6. Set state and status explicitly rather than relying on defaults.
  7. Seed anything that depends on plugin logic through the API, not through SQL.A direct insert bypasses every plugin and business rule, so any calculated field is empty or wrong and the inconsistency surfaces weeks later.
  8. Run the seed inside an explicit transaction, with the rollback rehearsed on the scratch copy.
  9. Capture row counts per table before and after, and store the pair.
Exit gate
STOPTransactional entities are not seeded

Reservations, orders, requests, service lines, clearances, selected pricing and evaluations hold the source organisation's operational history. Copied across, they reference customers, vouchers and users that mean something different here. The target starts with an empty ledger.

Duplicate detection silently drops rows

With detection enabled, an API seed reports success while skipping matches. Check the job output count against what you sent, not against what you expected.

Seed order is foreign key order, not alphabetical

Junctions inserted before their parents leave orphans that no screen shows and no error reports. Run the orphan check after every stage.

-- Orphan pattern. Repeat per junction; adjust the key columns to your schema.
SELECT 'Service-TimeSlot' AS Junction, COUNT(*) AS Orphans
FROM dbo.new_servicetimeslot j
LEFT JOIN dbo.new_rvservice s ON s.new_rvserviceId = j.new_serviceid
WHERE s.new_rvserviceId IS NULL
UNION ALL
SELECT 'Region-Resource', COUNT(*)
FROM dbo.new_regionresource j
LEFT JOIN dbo.new_rvresource r ON r.new_rvresourceId = j.new_resourceid
WHERE r.new_rvresourceId IS NULL;

-- Ownership: every seeded row belongs to a user that exists here.
SELECT COUNT(*) AS RowsWithUnknownOwner
FROM dbo.new_rvservice s
LEFT JOIN dbo.SystemUserBase u ON u.SystemUserId = s.OwningUser
WHERE u.SystemUserId IS NULL;

-- Transactional tables must still be empty.
SELECT 'Reservation' t, COUNT(*) c FROM dbo.new_reservation
UNION ALL SELECT 'SelectedHourlyPricing', COUNT(*) FROM dbo.new_selectedhourlypricing;
07

Verification and regression

· The module works, and nothing else broke
Walk one complete booking from configuration to clearance, then prove the rest of the organisation is exactly as it was.
  1. Configure a test service.Region, timeslots, resource group, resources, parameters and a price list.
  2. Request available days from the web client.Exercises the availability procedure, the date functions and the calendar table together. An empty calendar here is almost always coverage.
  3. Request available resources for a chosen day and check the list and quantities.
  4. Price a service line with a promotion and reconcile the total against the same configuration in the source.
  5. Create a reservation from the web client and a second from mobile, and confirm both appear correctly in the CRM.
  6. Run the clearance and refund path through to a receipt voucher and confirm the regarding field resolves.
  7. Run the availability report and the FAQ counts and sanity-check them against the reservation you just made.
  8. Run the regression pack for every other live module.Pay particular attention to any screen that loads a merged web resource or a shared entity form.
  9. Repeat the whole walk as an ordinary module user.Administrators bypass privilege checks. Testing only as admin means the first real user finds the security gaps.
  10. Time the heavy availability procedures against realistic volumes and compare with the source.
Exit gate
A green module test says nothing about the other modules

The components most likely to have been damaged — shared scripts, shared forms, global option sets — are not exercised by module tests at all. The regression pack is the real test; the module walk is the easy half.

Empty results are the failure mode to expect

Missing calendar rows, an unresolved lookup, a filtered-out region: all of them return an empty list rather than an error. Treat every empty result as a defect to explain until proven otherwise.

Exit criteria for go-live
  • Every step of the walk passed as a non-administrator.
  • Regression green across the other modules.
  • No unexplained errors in either service log across the whole session.
  • Timings within the agreed margin.
08

Hand over and watch

· Close the change
Leave the target in a state someone else can support, and leave a record of what was done.
  1. Collect the sign-offs.
  2. Move the payment gateway out of sandbox and re-test one live transaction end to end.
  3. Lift the customisation freeze on both organisations and tell everyone it is lifted.
  4. Take a fresh backup of the target as the new known-good state.Keep the pre-migration backup until the watch window closes.
  5. Watch for 48 hours with a named on-call owner and a daily log review.
  6. Update the criteria sheet to its final state.Corrected classifications, merge decisions on shared components. The next organisation migrated starts from this sheet.
  7. Write the known-issues list and hand it to support with the release folder.
Exit gate
Do not delete the pre-migration backup at go-live

The defects this kind of migration produces — a shared script subtly broken, an option set remapped — surface days later, from a user in a module nobody tested.

Rollback

Where you can still turn back, and where you cannot.

STEPS 1–2

Free

Nothing has been written to the target. Abandoning costs only the time spent.

STEPS 3–4

Restore from backup

Restore the organisation and configuration databases together. Do not unpick an import by deleting components by hand.

STEPS 5–6

Restore, then re-point

Restore as above, revert the service configuration, revoke any credential issued for the target, and confirm nothing was written to the source.

AFTER GO-LIVE

Forward only

Once users transact in the target, restoring destroys their work. Every problem is now fixed by rolling forward.

The decision belongs to one person

Rollback decisions taken by committee mid-incident are taken late. One named owner calls it at each gate, with a timestamp and a reason.

Sign-off

Each gate is signed before the next step begins.
